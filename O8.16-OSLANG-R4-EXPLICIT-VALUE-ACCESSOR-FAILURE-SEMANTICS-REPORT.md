## Executive summary

R4 eliminated ambiguous value accessor failure behavior that disguised type mismatches as valid-looking values (`NaN`, `null!`, `0`, `NullValue`). Invalid value access is now explicit: `Value.TryAsX` accessors return a success flag, `StandardLibrary.NUMBER`/`StringOp` surface errors via `ctx.Throw()` instead of silent defaults, and the interpreter preserves a pending exception across sub-expression and statement boundaries instead of overwriting it with a generic error. OSLANG remains interpreted; no bytecode, compiler pipeline, or architectural redesign was introduced.

## Root causes confirmed

1. **`Value.AsNumber` returned `double.NaN`** for a non-number; `AsString`/`AsArray`/`AsObject`/… returned `null!` for a mismatched kind. These are indistinguishable from valid values, so callers could not detect failure. (All engine call sites happened to guard kind first, so the paths were dead, but the accessors themselves were latent hidden-failure indicators.)
2. **`StandardLibrary.NUMBER` returned `Value.Number(0)`** for a wrong arg count or non-numeric argument — a silent default.
3. **`StandardLibrary.StringOp` returned `Value.NullValue`** for a wrong argument type — callers continued with `NullValue`.
4. **`ExpressionEvaluator.EvaluateBinary`/`EvaluateCall`/`EvaluateMethodCall`** did not re-check `CurrentFlow` after evaluating sub-expressions, so a pending `Exception` from a failed sub-expression was overwritten by a generic "operator not supported" error (or a wrong `Null = Null → true` result).
5. **`StatementExecutor` Return/Break/Continue** unconditionally overwrote `CurrentFlow` after evaluating an expression, clobbering a pending `Exception` established by R1.

## Design decision and rationale

**Chosen model:** explicit `TryAsX` accessors on `Value` (bool + out) plus `ctx.Throw()` at the standard-library call sites plus flow preservation in the evaluator/statement executor.

**Why this model:**
- `Value` is a pure struct with no `ExecutionContext` dependency (architectural constraint: do not make `Value` depend on `ExecutionContext`). `TryAsX` makes failure explicit without that dependency — a caller must check the returned `bool` before using the `out` value, so failure cannot be mistaken for NaN/0/null!/NullValue.
- `AsX` properties remain as unchecked convenience getters. They are only invoked after kind validation in engine call sites (all such call sites guard kind first), so the NaN/null! paths are dead in practice. Rewriting all ~50 guarded call sites to `TryAsX` would be widespread, unrelated modification — explicitly discouraged by the task — so `AsX` is left for already-validated use. This is a documented limitation.
- `StandardLibrary.NUMBER` and `StringOp` now `ctx.Throw()` with contextual messages (location plumbed through) instead of returning `0`/`NullValue`. The original error is not replaced by a generic follow-up.
- `EvaluateBinary`/`EvaluateCall`/`EvaluateMethodCall` return `Value.NullValue` immediately when `CurrentFlow != Normal` after a sub-expression, so a pending exception propagates instead of being overwritten. `Return`/`Break`/`Continue` only set flow when currently `Normal`.
- OOM/recovery semantics are untouched (R2 already established OOM as hard/fatal). R4 does not promise TRY/CATCH recovery from type errors; it makes them observable through the existing soft-throw flow.

**Alternatives considered and rejected:**
- Making `AsX` throw `InvalidOperationException` on mismatch — would bypass the soft-throw `ControlFlow.Exception` flow (R8 concern: C# exceptions bypass soft-throw) and bypass location context. Rejected.
- Routing accessor failure through `ctx.Throw()` from inside `Value` — requires `Value` to depend on `ExecutionContext`, forbidden by constraint. Rejected.
- Rewriting all guarded call sites to `TryAsX` — widespread unrelated modification; out of scope. Rejected.

## Regression tests added and results

`host/CollectionTests/ValueAccessorTests.cs` (29 tests), grouped:

**Direct `Value.TryAsX` accessors:** correct number access; mismatched number→false; correct string access; mismatched string→false; correct array access; mismatched array→false; Null→TryAsObject false; correct boolean access; mismatched boolean→false.

**Interpreter-driven (standard library + evaluator):**
- `NUMBER` valid (5) → flow Normal, result 5.
- `NUMBER("abc")` → flow Exception, message "NUMBER expects a single numeric argument".
- `NUMBER()` (no args) → flow Exception, same message.
- `LEFT("hello", 2)` → flow Normal, result "he".
- `LEFT("hello", "x")` → flow Exception, message "Expected a string and a number argument".
- `LEFT(5, 2)` → flow Exception, same message.
- `(1 / 0) + "abc"` → flow Exception, message "Division by zero." (original error preserved, NOT overwritten by generic operator error).
- Function call `boom()` (which does `t = 1/0`) → flow Exception, message "Division by zero." (R1 propagation across call boundary preserved).
- `1 + 2` → flow Normal, result 3 (valid coercion preserved).
- `"a" + "b"` → flow Normal, result "ab" (valid coercion preserved).

Tests assert both flow state and error message/location where applicable, using deterministic inputs.

## Remaining limitations

- `AsX` properties still return NaN/null! on mismatch, but no engine call site reaches them unguarded. Wiring all call sites to `TryAsX` is deferred.
- R4 does not make type errors TRY/CATCH-recoverable (no such recovery guarantee exists in the architecture); it makes them observable through the existing soft-throw flow.
- Does not address R5 (test architecture), R7 (equality/Closure), R8 (C# exception vs soft-throw model), or R9 (host-level error surfacing).
